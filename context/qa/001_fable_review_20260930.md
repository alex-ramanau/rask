# rask code review (2026-09-30)

Reviewer role: senior Rust engineer. Scope: all of `src/`, `tests/`, `Cargo.toml`,
`.cargo/config.toml`, `.github/workflows/`, `snap/snapcraft.yaml` at commit `3b698af`.
The `scripts/` directory and `tools/regex-spike` were only skimmed.

## Overall impression

This is a careful, disciplined port. Strong points:

- **The spec comes first.** Every module names the Perl function it ports, and
  comments explain *why* things are done (e.g. `-r _` vs `-R` in
  `filetest.rs`, `(?^flags:…)` in `matcher/build.rs`). That makes the code easy
  to review against ack.
- **Bytes throughout** (`bytes.rs`). No lossy UTF-8 decoding on the hot path,
  and non-UTF-8 patterns are handled deliberately (`pattern_to_pcre`).
- **`unsafe_code = "forbid"`**, clippy is clean with `-D warnings`, and
  `cargo test --all` passes (40 tests).
- **The ordered parallel pipeline** (`parallel.rs`) is a nice design. All
  printing stays on one thread, workers capture warnings, and walk order is
  kept, so the output matches the serial search. Shutdown on early exit (`-1`,
  `-m`) works: dropping `Ordered` closes the channels and every thread returns.
- **Conformance tooling**: the ack3 suite, `diff-ack`, and the `-T` property test
  make a very strong safety net.

Most of the findings below are **gaps between the conformance suite and real
workloads**: long lines, pseudo-files, many arguments, large trees of big
files. The suite doesn't reach these, but real users will.

## How findings were verified

Findings marked **[verified]** were reproduced with the release binary. Where
it made sense, they were also compared against Perl ack 3.10.0, run from
`../ack3/blib` with File::Next from `~/perl5`. The others come from reading
the code.

Perl ack was also checked on three things that looked suspicious, and rask
already matches it there. None of these is an issue:

- `-m 0` stops `-f`/`-l` after the first file (`defined($opt_m) && …`).
- A symlink loop with `--follow` goes around until the kernel returns `ELOOP`
  (41 results in both). File::Next has no loop detection.
- A write error that isn't EPIPE (`> /dev/full`) still exits 0 in both.

## High

### 1. JIT stack exhaustion makes patterns silently miss matches

**Where:** `src/matcher/pcre.rs:40-52` (`find_at` maps `Err` to "no match"),
`src/matcher/pcre.rs:12-18` (JIT on, default JIT stack).

PCRE2's JIT uses a fixed stack of 32 KiB by default. Patterns with a repeated
group (`(a|b)*`, `(?:x|y)+`, `(\s*\w+)*`, …) need stack in proportion to the
line length. When the stack runs out, `find_at` returns
`Err("JIT stack limit reached")`. The comment says this is treated like Perl
giving up, but Perl does **not** give up here. rask just reports no match,
with no warning and exit code 1.

```
$ printf 'aaaa%.0s' $(seq 1 1500) > l.txt; echo >> l.txt    # one 6000-char line
$ rask --noenv -c '^(?:a|b)*$' l.txt
0
$ perl ack --noenv -c '^(?:a|b)*$' l.txt
1
```

The threshold is low: 1,000 chars matches, 5,000 does not. Minified JS/CSS,
JSON, lock files, SVG and logs have lines far longer than that. **This is the
most serious finding. A search tool that silently misses matches breaks
users' trust in it.**

The prescan makes it worse. `re_scan.is_match(&buf)` runs over the **whole
file buffer** (`search/mod.rs:384-389`), not one line. If the scan regex hits
the limit on a large file, `is_match` returns false and the whole file is
skipped.

A standalone test against pcre2 0.2.11 shows the cause and the fix:

| subject length | JIT (default stack) | JIT, 8 MiB stack | JIT, 64 MiB stack | no JIT (interpreter) |
|---|---|---|---|---|
| 5,000 | **Err: JIT stack limit** | match | match | match |
| 200,000 | **Err** | match | match | match |
| 2,000,000 | **Err** | **Err** | match | match |

**Recommendation:**

1. Keep a second `Regex` in `PcreMatcher` built with `jit_if_available(false)`,
   created lazily with `OnceLock`. When the JIT returns an error (code
   `-46`, `PCRE2_ERROR_JIT_STACKLIMIT`), run the match again on the
   interpreter. PCRE2 ≥ 10.30 keeps its backtracking frames on the heap, so it
   handles these subjects. Also raise the JIT stack
   (`max_jit_stack_size(Some(1 << 20..))`) so that fallback is rare.
2. If the interpreter also fails (match/heap/depth limit), **warn once per
   run** (e.g. `ack: regex match limit exceeded in FILE; results may be
   incomplete`) instead of dropping the error silently.
3. Add a regression test with a long line and a repeated group, for both the
   line matcher and the prescan.

### 2. Walked files with `st_size == 0` are cut off after 512 bytes

**Where:** `src/search/mod.rs:328-374` (`open_and_prescan`).

For a file found by the walk, the default `-T` filter has already opened it
and read the first `texttest::BLOCK` (512) bytes. `open_and_prescan` then asks
`fstat` for the size and reads only `min(size, 10M)` bytes in total. For
procfs, sysfs, configfs and many FUSE filesystems, `st_size` is 0 even though
the file has content. So `limit = 0`, `read_up_to` returns at once, and only
the 512-byte head is searched. Perl does a single `sysread` of up to 10 MB,
whatever `st_size` says.

```
$ rask --noenv -n -H ctxt_switches /proc/self/        # walked
(exit 1, no output)
$ rask --noenv -H ctxt_switches /proc/self/status     # explicit: no handle, so size = None
/proc/self/status:58:voluntary_ctxt_switches: 4
$ perl ack --noenv -n -H ctxt_switches /proc/self/
/proc/self/status:58:voluntary_ctxt_switches: 165
```

The same code also affects **files that grow** between the `fstat` and the
read, such as a log being appended to. rask stops at the old size, while Perl
reads to EOF (up to 10 MB). That difference is smaller, but it has the same
cause.

**Recommendation:** Use `st_size` only as a *capacity hint*, not as the limit.
Reserve `size` bytes, read until EOF or `PRESCAN_SIZE`, and remove the
`size.is_some()` special case. If saving the extra `read()` that returns 0
matters for performance, keep it only when `size > 0` and the filesystem is
known to report sizes, but the simple fix is to always read to EOF. Add a
test that walks `/proc/self` on Linux (behind `cfg(target_os = "linux")`).

### 3. Parallel pipeline memory is limited by entry count, not bytes

**Where:** `src/parallel.rs:33-35` (`WINDOW = 256`), `src/search/mod.rs:350-395`.

Each `Prepared::Searched` result holds the file's **entire contents** (up to
`PRESCAN_SIZE` = 10 MB) plus a `Vec<u32>` match table (4 bytes per line). The
window lets up to 256 of these wait for the printer. If the printer is slow on
one item, the workers keep filling the window. That happens with a file over
10 MB that the main thread streams line by line, a slow pager or pipe reader,
or heavy `--color` output. Peak RSS is then about 256 × (file size + table).

Measured on 1 × 300 MB file followed by 60 × 9 MB files, all matching:

| mode | wall | max RSS |
|---|---|---|
| `rask needle .` (parallel) | 1.37 s | **575 MB** |
| `RASK_THREADS=1 rask needle .` | 1.68 s | 13.5 MB |
| `rask -c needle .` (parallel) | 0.33 s | 49 MB |

With 256 such files the peak would be about 2.5 GB. That can get the process
OOM-killed on a CI runner or a small VM, all to gain about 20% wall time.

**Recommendation:** Add a **byte budget** alongside the entry window, e.g. a
counting semaphore of 64–128 MB of buffered file data. A worker acquires
`buf.len()` bytes before reading the file, and the consumer releases them when
it drops the `Opened`. Always let an oversize single item through so the
pipeline can't deadlock. As a cheaper partial fix, drop the table and the
buffer for files whose prescan fails *before* sending (this already happens),
and consider keeping only the matched lines' byte ranges instead of the whole
buffer when there's no context (`-A/-B/-C`, `--passthru`, `-v`).

## Medium

### 4. One bad combined regex silently disables every `match:` filter in a collection

**Where:** `src/filter/mod.rs:271-275`

```rust
self.big_re = PcreMatcher::from_bytes(&self.match_parts.join(&b"|"[..])).ok();
```

Each `match:` filter compiles on its own, but the combined
`(?:A)|(?:B)|…` may not compile. The most likely case is two filters that use
the same named group, which Perl accepts and PCRE2 rejects unless `DUPNAMES`
is on. `.ok()` then sets `big_re = None`, and **every** `match:` filter in
that collection stops working, with no message. This affects `--ignore-file`,
`--ignore-dir=match:` and `--type-add=x:match:`.

```
$ rask --noenv '--ignore-file=match:/^(?<n>foo)/' '--ignore-file=match:/^(?<n>bar)/' -l hit
bar.txt
baz.txt
foo.txt          # neither filter applied
$ perl ack --noenv (same)
baz.txt
```

**Recommendation:**

- Build the group with `(?J)` (PCRE2 `DUPNAMES`) in front, which matches Perl.
- Never use `.ok()` here. If the combined regex still fails, keep a
  `Vec<PcreMatcher>` of the individual filters and match them one by one
  (slower but correct).
- A smaller point: `add` rebuilds the combined regex on every insertion, which
  is O(n²) in the number of filters. Build it once, when the collection is
  finished (see #8).

### 5. Option parsing is quadratic in the number of arguments

**Where:** `src/cli/getopt.rs:491-492` (`argv.remove(0)`), plus the
`argv.insert(0, …)` calls in `find_option` / `finish_lookup`.

Every Getopt pass pops from the **front** of a `Vec`. The ARGV source goes
through about 9 such passes: early help, `retrieve_arg_sources`,
`remove_default_options_if_needed`, `--dump`, `process_filetypes`, two
`mutex::check` passes, `--help-types`, and the main pass. The two `mutex::check`
passes also clone argv. With `xargs rask pattern` or `rask pattern $(git
ls-files)`, argument counts in the tens of thousands are normal.

Measured with `rask --noenv -f -m1 <N files>`. That command dies in
`mutex::check` before any file I/O, so this is pure option parsing:

| N | 10,000 | 40,000 |
|---|---|---|
| time | 0.09 s | 1.10 s |

And a full `-c` search over N one-line files: 5k 0.04 s → 10k 0.11 s → 20k 0.42 s
→ 40k 1.54 s. That's about ×4 per doubling.

**Recommendation:** Use a `VecDeque<Bytes>` inside `get_options_with_nonoptions`
(`pop_front`/`push_front`), converting at the boundary if you want to keep the
public `&mut Vec<Bytes>` signature. It's a small change, and the getopt unit
tests cover it well.

### 6. A worker panic hangs the process

**Where:** `src/parallel.rs:80-87, 128-155, 165-187`

Workers are detached `thread::spawn`s. If one panics while handling entry
`seq = k`, for example on an `unwrap()` in the selector, a poisoned mutex
(`idir.collection.lock().unwrap()`) or any future bug, then:

- `Done` for `k` is never sent.
- `Ordered::next` waits in `results.recv()` forever, because the other workers
  still hold `done_tx` clones.
- The walker runs out of tokens and blocks, and the other workers sit idle.

The user sees a panic message on stderr, and then the process **hangs
forever** instead of exiting with an error. In a script or CI job, that
turns a crash into a timeout.

**Recommendation:** Either

- set `panic = "abort"` in `[profile.release]` (simple, and a CLI loses
  nothing by it), or
- wrap each job in `std::panic::catch_unwind` and send a `Done` carrying a
  fatal error, which `Ordered::next` turns into a `die()` with a clear message.

Do the same for the walker thread: if it panics, the stream just ends early,
and the run succeeds with **silently incomplete results**.

### 7. The declared MSRV is wrong

**Where:** `Cargo.toml:4` (`rust-version = "1.85"`)

The code uses let-chains throughout (`if let … && let …`, e.g.
`app.rs:497`, `search/mod.rs:383`, `filter/mod.rs:564`). Let-chains were
stabilized in **Rust 1.88** (edition 2024). A user or distro packager on
1.85–1.87 passes the `rust-version` check and then gets a compile error.
CI only tests `stable`, so this was never caught.

**Recommendation:** Set `rust-version = "1.88"` (check the other recent APIs
too, e.g. `std::iter::repeat_n` 1.82 and `<[u8]>::trim_ascii` 1.80, which are
both fine), and add an MSRV job to CI
(`dtolnay/rust-toolchain@1.88` + `cargo check --locked`).

## Low

### 8. `Arc<Mutex<Collection>>` for data that never changes after parsing

**Where:** `src/config/mod.rs:42-46`, used at `src/app.rs:461` (descend filter,
once per directory) and `src/app.rs:523` (per file per directory level, in
every worker, with `--noignore-dir`).

The `Mutex` only exists so `add_ignore_dir` can append to the last collection
while options are parsed. After that the collection is read-only. Workers
still take the lock, so they contend with each other, and a poisoned lock
leads to the hang in #6. `Collection` is already `Send + Sync`.

**Recommendation:** Build with a plain `Vec<(Collection, bool)>` in `Opt`, then
**freeze** it into `Arc<[IgnoreDir]>` with `Arc<Collection>` (or no `Arc` at
all, inside `SelectorData`) at the end of `process_args`. This also fits well
with building `big_re` once (#4).

### 9. The eval-group check fires inside character classes

**Where:** `src/matcher/perl_syntax.rs:291-304`

`check` searches the raw pattern for `(?{` / `(??{` before any parsing, so
`[(?{]` (a class of three literal characters) is rejected:

```
$ rask -c '[(?{]' e.txt   → ack: Invalid regex '[(?{]' …
$ perl ack -c '[(?{]' e.txt → 1
```

It is a rare case, but the fix is easy: detect eval groups in
`group_header` (for `b'{'` and `b'?'` followed by `{`), where class and
escape context are already known.

### 10. Thread-local stdout is an unchecked invariant

**Where:** `src/output/mod.rs:23-45`

`OUT` is `thread_local!`. Only the main thread's buffer is flushed in `exit()`,
and the pager is attached only to the main thread's `Out`. Today only the main
thread prints, and warnings on workers are captured, so this works. But
nothing enforces it. A future `output::print` from a worker, even a debug
line, would go to a separate 64 KB `BufWriter` that is **never flushed**.

**Recommendation:** Add a `debug_assert!` that `print` runs on the main
thread (store the main `ThreadId` in a `OnceLock` at startup), or document
the invariant in `parallel.rs`'s module docs next to "Everything that depends
on what was printed before …".

Related points:

- **BrokenPipe:** `exit(141)` skips waiting for the pager, and skips any
  remaining flush. That's fine in practice, but a parent that checks
  `WIFSIGNALED` sees a different result than it would from Perl being killed
  by SIGPIPE.
- **Other write errors:** these are ignored, which matches Perl. Worth a
  comment, so nobody "fixes" it later.

### 11. Match table built for the whole buffer even when output stops early

**Where:** `src/search/mod.rs:390, 408-418`

For every file that passes the prescan, the worker runs `re_match` (and
`re_not`) on **every line** of the up-to-10 MB buffer. Early exits (`-1`,
`-m N`) and `--range-start/--range-end` mean most of that work may be thrown
away. Workers do the work, so throughput for other files suffers, and the
table also adds to the memory in #3.

**Recommendation:** Skip the table when `max_count` is small, or when ranges
are used. The printer's `None => self.s.matches(line)` path already handles
that. Alternatively, build the table lazily in chunks.

### 12. Smaller cleanups

- **`walk/mod.rs:282-286`**: `.by_ref().take(u64::MAX)` is a no-op. Use
  `self.reader.read_until(b'\n', &mut line)` directly.
- **`app.rs:491-492`**: `Selector::select` clones the `Arc` on every call just
  to satisfy the borrow checker. Destructure `self` instead
  (`let Selector { data, previous_dir, previous_dir_ignore_result } = self;`).
- **`app.rs:506`**: when any start is a file, `get_file_id` does an extra
  `stat` for **every** walked file. You could compare `(dev, ino)` only for
  walked files whose basename matches a start's basename, or keep the set of
  start paths after `reslash`/`canonpath` and compare those first.
- **`filter/texttest.rs:43`**: `looks_like_text` is `pub` and indexes
  `buf[len - 1]` on Windows without checking for an empty buffer. `is_text`
  guards against that, but the function itself is a panic waiting to happen.
  Add `len > 0 &&`.
- **`env.rs:38-47`**: `with_overrides` isn't unwind-safe. A panicking test
  leaves the overrides installed for the rest of that thread. Use a drop
  guard.
- **`output/mod.rs:145-148`**: the pager uses `/bin/sh` on every platform. On
  Windows (which CI builds), use `cmd /C`, or document that it's unsupported.
- **`lib.rs`**: every module is `pub`, which makes the whole port an accidental
  public API. Since `publish = false`, it's harmless now. Before publishing,
  make modules `pub(crate)` or `#[doc(hidden)]`, and expose only what
  `tests/` needs.
- **`tests/ack3_filters.rs:14-27`**: without `ACK3_DIR` the tests print
  "skipping" and **pass**. The `rust` CI job therefore reports 7 passing tests
  that never ran. Mark them `#[ignore]` and run them with `--include-ignored`
  in the `ack-suite` job, or fail when `CI=true` and the checkout is missing.
- **CI**: the ack3 suite step "reports pass counts without failing the job",
  so a regression on Linux (where the suite is green) goes unnoticed.
  Consider failing on Linux only, and keep the report-only mode for
  macOS/Windows.
- **`tmp/`** (where this review lives) isn't in `.gitignore`.

## Suggested order of work

1. **#1 (JIT fallback)** and **#2 (read to EOF)**: small, local changes that
   fix wrong results. Add regression tests for both.
2. **#4 (DUPNAMES + no `.ok()`)**, same reasoning, and very small.
3. **#6 (`panic = "abort"`)** and **#7 (MSRV)**: each is a one-line change.
4. **#5 (`VecDeque` in getopt)**.
5. **#3 (byte budget)**: the only item here that needs design work. It pairs
   well with **#8** and **#11**.

Suggested additions to `tests/diff/`, since they're cheap and catch the
high-severity items against Perl directly:

- a long-line / repeated-group case;
- a `/proc/self` walk (Linux only);
- two `--ignore-file=match:` filters with the same group name.
